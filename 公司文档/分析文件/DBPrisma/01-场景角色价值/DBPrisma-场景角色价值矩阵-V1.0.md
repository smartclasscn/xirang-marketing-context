## 1. 分析原则

### 1.1 以角色任务为中心，而不是按职位名称堆受众

同一个自然人可能同时承担技术决策、预算审批、安全责任和项目推动等多个角色。矩阵中的“角色”是其在数据库治理、系统建设或采购决策中承担的任务，不是固定职位。实际客户访谈时，应识别其当前承担的角色组合。

### 1.2 价值表达从客户任务和失败代价出发

每个场景均需回答：

1. 客户要完成什么任务；
2. 当前流程、系统或组织机制在哪里遇到困难；
3. 哪个角色最直接承受问题；
4. 谁发起、评估、批准、使用或集成产品；
5. 如果问题不解决，会造成什么业务、技术、安全或管理代价；
6. DBPrisma 哪些已实现能力或可扩展方向能够切入；
7. 客户可以观察或衡量什么变化；
8. 应当用什么内容、演示或证据让客户理解价值。

### 1.3 区分产品事实、场景支持与扩展方向

- 已实现能力：可围绕具体功能使用“实现”“具备”等表达。
- 场景支持：可使用“支持”“可用于”“为……提供基础”等表达。
- 可扩展方向：保留需求识别、方案研究和市场沟通，不写成当前已实现或已支持功能。
- SQL 方言转换：作为独立的可扩展方向保留；当前尚未开发，不得写入 DBPrisma 当前功能清单或当前能力承诺。

## 2. 客户角色体系

### R1. 企业经营与业务决策者

**典型角色：** 企业负责人、分管数字化/信息化的管理者、业务部门负责人、项目建设负责人。

- **核心任务：** 保证核心业务系统稳定运行；控制数字化建设和系统改造成本；推动数据库国产化、系统升级、数据治理或安全整改。
- **主要困境：** 数据库问题常被视为技术部门内部问题；系统改造风险和停机影响难以评估；投入与业务收益之间缺乏清晰对应。
- **关键决策：** 是否立项、是否投入预算、是否接受分阶段实施、是否允许在现有系统前增加治理组件。
- **失败代价：** 核心业务中断、项目延期、重复建设、迁移失败、审计整改和管理责任风险。
- **关注指标：** 业务连续性、项目周期、改造成本、风险降低程度、系统可维护性、投资回报。
- **产品触点：** 统一接入、数据库迁移治理、访问安全、运行可观测、遗留系统分析。
- **有效观点：** “不必一开始就重写业务系统，可以先在数据库访问路径上建立统一治理入口，再按业务节奏推进安全治理和系统改造。”
- **内容形式：** 管理层简报、场景方案、改造路径图、项目收益与风险分析。

### R2. CIO/CTO、信息中心负责人及企业架构负责人

**核心任务：** 规划数据库和应用架构；统筹数据库平台、基础软件、系统集成和安全体系；控制技术路线与供应商依赖。

- **主要困境：** 多种数据库并存，接入方式和治理能力分散；应用与数据库耦合较深；系统升级或数据库替代缺乏渐进路径；管理平台之间数据割裂。
- **关键决策：** 技术架构选型、部署模式、产品引入边界、兼容范围、集成方式、演进路线。
- **失败代价：** 架构复杂度持续增加、技术锁定、系统迁移失败、重复采购、平台不可持续。
- **关注指标：** 架构一致性、接入改造量、兼容范围、系统可扩展性、运维复杂度、迁移风险。
- **产品触点：** 代理接入、连接治理、路由、多后端处理、SQL 解析、管理接口、AI 扩展。
- **有效观点：** “DBPrisma 将数据库访问入口、连接治理、安全控制和行为采集组合到一条可管理的访问链路中，为异构数据库环境和渐进式架构演进提供基础。”
- **内容形式：** 总体架构图、部署拓扑、技术白皮书、架构对比、集成方案。

### R3. 数据库管理员与数据库平台运维人员（DBA）

**核心任务：** 保障数据库稳定运行；管理连接、账号、性能和后端节点；定位异常 SQL 和数据库访问问题；配合备份、迁移和升级。

- **主要困境：** 连接来源分散，应用侧连接配置难统一；SQL 行为和调用来源难追踪；多后端访问策略难维护；问题定位依赖数据库自身日志和人工协作。
- **关键决策：** 接入方式、连接池参数、路由策略、监控指标、运行维护流程。
- **失败代价：** 连接耗尽、故障定位时间增长、误操作、业务访问异常、切换和迁移风险。
- **关注指标：** 连接数、连接成功率、后端健康状态、SQL 执行耗时、故障发现与定位时间、运维操作量。
- **产品触点：** 连接池、多路复用、读写分离、负载分配、健康管理、熔断、CLI、Prometheus、Capture。
- **有效观点：** “把数据库连接和访问路径集中到网关管理，让 DBA 能从统一入口观察和治理数据库访问。”
- **内容形式：** 快速入门、部署指南、配置示例、监控指标说明、故障排查手册、现场演示。

### R4. 网络安全、数据安全与安全运营人员

**核心任务：** 建立数据库访问安全控制；识别异常访问和高风险 SQL；执行安全策略；与 SOC/SIEM、安全审计和应急响应体系协同。

- **主要困境：** 数据库访问路径分散；安全策略落在不同应用和数据库中；数据库操作行为难以集中观察；安全事件调查缺少统一数据。
- **关键决策：** 安全控制点、访问策略、审计字段、日志输出、与现有安全平台的集成方式。
- **失败代价：** 非授权访问、敏感数据风险、攻击行为难发现、事件追溯困难、整改压力。
- **关注指标：** 未授权访问拦截、异常 SQL 发现、审计覆盖范围、日志完整性、事件定位时间、策略误报/漏报。
- **产品触点：** IP 访问控制、身份认证、TLS/国密链路、认证失败限制、SQL 防火墙、预编译语句防护、行为审计、脱敏、外部审计数据输出。
- **有效观点：** “将数据库访问控制和 SQL 行为审计前置到统一访问入口，形成可管理、可追溯的数据库访问安全链路。”
- **内容形式：** 安全架构图、策略配置演示、审计样例、攻防场景说明、合规整改方案。
- **边界：** 不把 DBPrisma 描述为覆盖所有数据安全领域的综合安全平台，不承诺未实现的表级/列级权限控制或所有 SQL 风险的绝对拦截。

### R5. 应用研发负责人、软件架构师与开发团队

**核心任务：** 维护应用数据库访问逻辑；管理数据库驱动和连接池；配合数据库升级、替代和系统改造；定位 SQL 行为和业务逻辑问题。

- **主要困境：** 数据库访问逻辑散落在大量应用代码中；更换数据库时应用改造量大；遗留系统文档缺失；真实 SQL 行为与业务流程之间缺少关联。
- **关键决策：** 是否引入代理层、连接配置如何调整、应用改造范围、数据库兼容方案、如何使用 SQL 行为数据。
- **失败代价：** 代码改造量大、回归测试范围扩大、迁移延期、业务逻辑误判、维护成本上升。
- **关注指标：** 应用改造工作量、数据库访问兼容性、回归测试范围、故障定位时间、代码维护成本。
- **产品触点：** 代理接入、透明透传、连接治理、SQL 采集、SQL Parser、行为分析、异构数据库统一接入。
- **有效观点：** “通过数据库访问入口获取真实 SQL 行为，为应用维护、数据库替代和遗留系统理解提供可观察的数据依据。”
- **内容形式：** 接入前后架构图、代码改造边界说明、SQL 行为分析案例（须有授权证据）、开发者接入指南。
- **边界：** SQL 方言转换当前未开发；不能向研发团队承诺通过 DBPrisma 自动消除数据库方言差异。

### R6. 遗留系统负责人、软件维护与系统接管团队

**核心任务：** 接管缺乏文档或原开发团队已离场的系统；理解系统数据库访问行为；控制维护风险；制定升级改造路径。

- **主要困境：** 业务逻辑沉淀在代码和数据库操作中；缺少设计文档；调用方和 SQL 的业务含义不清楚；改动前无法准确评估影响范围。
- **关键决策：** 如何获取真实运行行为、如何识别系统依赖、先治理还是先重构、如何分阶段接管。
- **失败代价：** 改造引发隐性业务故障、维护周期延长、关键人员依赖、系统无法持续演进。
- **关注指标：** 数据访问行为覆盖度、SQL 归类效率、依赖识别程度、影响分析时间、维护人员理解成本。
- **产品触点：** SQL 流量采集、Parser、访问身份和来源信息、AI 分析扩展。
- **有效观点：** “先观察系统真实的数据访问行为，再逐步理解业务操作和数据库依赖，为系统接管与升级改造提供依据。”
- **内容形式：** 遗留系统接管方法论、SQL 行为分析流程、业务操作路径示意、分阶段改造方案。
- **边界：** DBPrisma 提供行为数据和分析基础，不等于自动还原全部源代码、需求文档或完整业务逻辑。

### R7. IT 运维、平台工程与自动化运维团队

**核心任务：** 管理数据库接入基础设施；配置和监控网关；将数据库治理纳入统一运维、监控和自动化平台。

- **主要困境：** 配置管理分散；运行指标不统一；重复性操作依赖人工；现有运维平台缺少数据库访问层数据。
- **关键决策：** 监控接入、命令管道使用、配置管理、自动化权限和变更流程。
- **失败代价：** 误配置、故障恢复慢、操作不可追溯、运维自动化难以规模化。
- **关注指标：** 配置变更成功率、故障发现时间、恢复时间、自动化覆盖度、运维操作效率。
- **产品触点：** CLI、Admin HTTP/HTTPS、Prometheus、配置预检、热重载、备份回滚、命令管道、Capture 数据管道。
- **有效观点：** “DBPrisma 不仅提供数据库访问控制，也提供可集成的管理、监控和数据接口，便于纳入现有运维体系。”
- **内容形式：** 自动化接入说明、监控面板示例、运维流程图、接口文档。

### R8. 内部审计、合规与风险管理人员

**核心任务：** 监督数据库访问是否符合制度要求；获取审计记录；支持内部检查、合规检查和事件调查。

- **主要困境：** 审计记录分散且格式不统一；业务部门与技术部门对访问行为解释不一致；审计取证需要多方协作。
- **关键决策：** 审计范围、留存策略、数据字段、报告流程和证据交付方式。
- **失败代价：** 无法及时还原操作过程、审计发现无法闭环、整改成本增加。
- **关注指标：** 审计覆盖度、记录可追溯性、取证耗时、异常发现率、整改闭环周期。
- **产品触点：** SQL 行为采集、身份与来源记录、执行结果与耗时、脱敏、结构化日志输出。
- **有效观点：** “为数据库访问过程建立可追溯的结构化记录，让审计从分散日志收集转向统一访问行为采集。”
- **内容形式：** 审计流程图、记录字段说明、审计样例、检查清单。
- **边界：** 产品输出审计数据不等于自动满足所有行业合规要求；留存、取证和报告制度仍由客户治理体系确定。

### R9. 外部系统集成商、行业软件商与解决方案提供商

**核心任务：** 将数据库访问治理、安全和审计能力集成进项目方案；为客户提供数据库迁移、系统改造或平台建设服务。

- **主要困境：** 不同客户数据库环境差异大；项目需要同时处理连接、安全、审计和后端路由；自研相同能力投入高。
- **关键决策：** 是否将 DBPrisma 纳入方案、接口适配方式、交付分工、售后责任和联合方案边界。
- **失败代价：** 项目集成周期拉长、交付责任不清、重复开发、客户现场问题难定位。
- **关注指标：** 集成周期、适配工作量、部署复杂度、接口稳定性、项目交付可复制性。
- **产品触点：** 统一代理接入、路由、安全策略、审计输出、管理接口、命令管道、多语言客户端。
- **有效观点：** “将数据库访问代理、安全防护和行为审计作为可组合的基础能力嵌入行业解决方案，减少项目重复建设。”
- **内容形式：** 合作伙伴方案包、集成架构、接口说明、联合演示和交付边界清单。

### R10. 数据库厂商、数据库迁移服务商与技术生态伙伴

**核心任务：** 推进数据库兼容适配、迁移验证、联合解决方案和生态合作。

- **主要困境：** 数据库产品之间协议、SQL、类型和事务语义存在差异；客户迁移项目需要并行验证和访问治理；生态合作缺少可复用的接入层。
- **关键决策：** 兼容认证、联合测试、适配范围、迁移方案、联合市场推广。
- **失败代价：** 适配周期延长、项目风险增加、客户问题归属不清、联合方案难复制。
- **关注指标：** 兼容测试覆盖、适配周期、项目成功率、联合方案复用率、问题闭环时间。
- **产品触点：** 统一代理接入、多后端路由、写广播、SQL Parser、审计与管理接口。
- **有效观点：** “以统一访问和流量治理层配合数据库厂商及迁移服务商，构建分阶段验证和迁移实施路径。”
- **边界：** 当前支持的数据库类型和兼容范围按实际版本及证据确认；SQL 方言转换属于未开发的可扩展方向，不得作为现有兼容承诺。

## 3. 场景—角色—价值总矩阵

说明：主角色是最直接承受问题或推动项目的人；关键协同角色参与决策、评估、使用或交付。一个项目通常涉及多个角色，不应将场景只卖给单一职位。

| 场景 | 主角色 | 关键协同角色 | 客户任务/核心痛点 | DBPrisma 价值切入点 | 主要价值结果 |
| --- | --- | --- | --- | --- | --- |
| S1 数据库访问安全治理 | R4 安全运营 | R1、R2、R3、R8 | 统一控制数据库入口，减少分散访问风险 | 代理入口、身份校验、IP 控制、TLS/国密、SQL 防火墙、审计 | 安全策略集中、访问行为可追溯 |
| S2 数据库行为审计与运行分析 | R8 内部审计；R4 安全运营 | R3、R2、R7、R5 | 还原谁在何时从何处执行了什么数据库操作 | SQL 采集、身份来源、执行结果与耗时、脱敏、结构化输出 | 审计取证效率提升，运行行为可观察 |
| S3 数据库连接治理与访问路径统一 | R3 DBA | R2、R7、R5 | 统一多应用连接和后端访问路径 | 代理接入、连接池、多路复用、读写分离、负载分配、健康管理 | 连接治理集中，访问路径可管理 |
| S4 数据库迁移与渐进式替代 | R2 架构负责人 | R1、R3、R5、R10、R9 | 控制数据库替代的业务影响和切换风险 | 统一接入、多后端路由、写广播、流量采集与分析 | 为并行验证、分阶段替代提供访问治理基础 |
| S5 异构数据库统一接入与并发访问 | R2 架构负责人 | R3、R5、R9、R10 | 在多种数据库并存环境下统一管理访问入口 | 代理接入、连接治理、路由、管理接口 | 访问入口统一，减少接入治理分散 |
| S6 遗留系统分析、维护与升级改造 | R6 系统接管团队 | R5、R2、R1、R3 | 理解缺少文档系统的真实数据访问行为 | SQL 采集、Parser、调用来源信息、AI 分析扩展 | 为系统接管、依赖分析和改造评估提供依据 |
| S7 业务孪生与数据访问行为建模 | R2 架构负责人；R1 业务决策者 | R5、R6、R7、R8 | 建立业务运行过程与数据访问行为之间的关联 | SQL 与行为采集、语义处理、AI 分析、数据接口 | 为业务过程建模提供持续数据来源 |
| S8 AI 驱动的数据库治理与软件理解 | R2 架构负责人 | R3、R4、R5、R6、R7 | 将访问数据转化为分析、配置优化和自动化治理 | 分层 AI 接口、SQL/行为数据、管理接口和数据管道 | 形成数据驱动的分析和治理扩展路径 |
| S9 SQL 方言转换（独立扩展方向） | R2 架构负责人 | R5、R10、R9 | 解决源/目标数据库 SQL 语法和语义差异 | 当前仅有完整 SQL Parser 这一基础；方言转换能力尚未开发 | 作为未来独立能力方向，服务数据库迁移和异构整合需求 |

## 4. 场景价值拆解与市场表达

### S1. 数据库访问安全治理

- **首要购买动因：** 数据库安全风险治理、访问入口收敛、统一安全策略。
- **典型触发事件：** 安全检查发现数据库访问分散；账号治理困难；发生异常 SQL 或非授权访问事件；需要强化数据库入口控制。
- **决策链：** 安全负责人提出问题 → DBA/架构团队评估接入 → 信息化负责人确定方案 → 管理层或预算负责人批准。
- **核心观点：** 数据库安全不能只依赖应用系统和数据库自身配置，还需要在数据库访问路径上建立统一控制点。
- **建议演示：** 应用经 DBPrisma 接入；展示来源控制、认证、SQL 防火墙规则、审计记录。
- **价值衡量：** 访问入口覆盖范围、策略集中管理程度、异常访问追溯时间、审计数据完整度。
- **内容优先级：** 高。

### S2. 数据库行为审计与运行分析

- **首要购买动因：** 需要还原数据库访问行为，支撑审计、故障定位和运行分析。
- **典型触发事件：** 安全事件调查；审计整改；数据库性能问题难定位；应用团队无法说明某类 SQL 的来源。
- **决策链：** 审计/安全/DBA提出需求 → 技术团队验证采集字段与性能影响 → 信息化负责人批准。
- **核心观点：** 只有把 SQL 与访问身份、来源、时间、目标后端和执行结果关联起来，数据库访问才真正具备可追溯性。
- **建议演示：** 展示 SQL 采集、执行耗时、身份来源、脱敏和结构化输出。
- **价值衡量：** 取证耗时、SQL 来源识别率、审计覆盖范围、故障定位时间。
- **内容优先级：** 高。

### S3. 数据库连接治理与访问路径统一

- **首要购买动因：** 连接管理复杂、多应用访问配置分散、数据库后端多。
- **典型触发事件：** 连接数增长；后端扩容；读写分离需求；数据库连接故障频发；需要集中管理数据库入口。
- **决策链：** DBA提出需求 → 架构团队设计接入方式 → 运维团队评估部署与监控 → 信息化负责人批准。
- **核心观点：** 数据库连接不应完全散落在每个应用中，统一入口能够把连接和访问路径变成可治理对象。
- **建议演示：** 展示应用连接改向网关、连接池状态、后端健康和读写路由。
- **价值衡量：** 连接治理集中度、连接异常定位时间、配置变更工作量、后端故障隔离效果。
- **内容优先级：** 高。

### S4. 数据库迁移与渐进式替代

- **首要购买动因：** 需要降低数据库替代或迁移对业务系统的冲击。
- **典型触发事件：** 国产数据库替代；旧数据库升级；核心系统数据库更换；多个后端需要并行验证。
- **决策链：** 项目负责人/架构师提出迁移路径 → DBA和研发团队验证 SQL 与数据行为 → 数据库厂商/迁移服务商参与 → 管理层批准实施。
- **核心观点：** 数据库迁移不只是数据搬运，也需要治理应用访问路径和迁移期间的数据库流量。
- **建议演示：** 以受控环境演示统一入口、多后端路由、写广播配置和 SQL 行为观察；明确演示不等于完整迁移工具。
- **价值衡量：** 应用改造量、并行验证覆盖、切换准备周期、回退准备程度、迁移期间异常定位时间。
- **内容优先级：** 高。
- **边界：** 不承诺自动数据同步、异构 SQL 自动转换或无损迁移。

### S5. 异构数据库统一接入与并发访问

- **首要购买动因：** 企业有多种数据库并存，需要统一接入和访问治理。
- **典型触发事件：** 多数据库平台建设；集团内数据库类型多；应用需要访问多个后端；数据库资源整合。
- **决策链：** 架构负责人提出统一接入要求 → DBA和研发确认驱动及协议适配 → 集成商评估项目集成。
- **核心观点：** 数据库类型可以不同，但访问入口和治理方式可以先统一。
- **建议演示：** 在明确支持范围内，展示不同数据库后端经统一代理入口接入和管理。
- **价值衡量：** 接入方式统一程度、适配工作量、运维复杂度、后端访问治理能力。
- **内容优先级：** 中高。
- **边界：** 统一接入不代表统一 SQL 方言；方言转换另列为未开发扩展方向。

### S6. 遗留系统分析、维护与升级改造

- **首要购买动因：** 系统缺乏文档、原团队离场、维护成本过高或升级改造风险不可控。
- **典型触发事件：** 系统接管；人员交接；国产化改造；系统重构；故障频发但原因不明。
- **决策链：** 系统负责人提出问题 → 维护团队定义观察范围 → DBA/研发分析 SQL 行为 → 架构负责人确定改造路径。
- **核心观点：** 对缺少文档的系统，先观察真实数据库访问行为，再逐步理解数据访问路径和业务依赖。
- **建议演示：** 对授权的测试系统采集 SQL，按来源、类型、目标数据库和时间分析访问行为；展示如何形成后续分析材料。
- **价值衡量：** 访问行为识别效率、依赖分析时间、系统接管周期、改造前影响评估质量。
- **内容优先级：** 高。
- **边界：** 不承诺自动生成完整业务文档或还原全部源代码逻辑。

### S7. 业务孪生与数据访问行为建模

- **首要购买动因：** 希望从系统运行数据理解业务过程，建立可持续更新的业务运行模型。
- **典型触发事件：** 业务流程数字化；业务运行监测；系统整合；业务流程优化。
- **决策链：** 业务负责人定义建模目标 → 架构和数据团队确定实体与事件 → 技术团队建立数据关联 → 管理层评估业务价值。
- **核心观点：** 数据库访问行为是业务系统执行过程的重要观测窗口，可为业务过程建模提供持续数据来源。
- **建议演示：** 从一组授权测试 SQL 出发，关联访问身份、时间、目标数据对象和执行结果，形成业务操作轨迹示意。
- **价值衡量：** 业务事件覆盖度、状态关联准确度、过程还原效率、模型更新及时性。
- **内容优先级：** 中高。
- **边界：** DBPrisma 是数据采集和分析基础，不是完整业务孪生平台本身。

### S8. AI 驱动的数据库治理与软件理解

- **首要购买动因：** 希望利用 AI 降低 SQL 分析、运行治理和遗留软件理解的人工成本。
- **典型触发事件：** SQL 数量和复杂度增长；运维人员不足；遗留系统理解困难；希望把监控数据转化为治理动作。
- **决策链：** 架构/运维/研发提出用例 → 数据安全人员确认数据边界 → 技术团队连接 AI 接口和数据管道 → 负责人确定自动化权限。
- **核心观点：** 数据库访问链路产生的 SQL 和行为数据，可以成为 AI 理解数据库运行和软件行为的重要上下文。
- **建议演示：** 展示 SQL 与行为数据进入分析流程，输出分类、解释或配置建议；自动执行必须有明确权限和审计边界。
- **价值衡量：** SQL 分析效率、问题定位时间、建议采纳率、人工操作减少量、自动化执行成功率。
- **内容优先级：** 中高。
- **边界：** 不宣传当前已实现全自动自治运维或完全自动化软件理解。

### S9. SQL 方言转换（独立扩展方向）

- **首要需求方：** 数据库迁移项目负责人、企业架构师、应用研发负责人、数据库厂商和迁移服务商。
- **客户问题：** 源数据库和目标数据库之间 SQL 语法、函数、类型及执行语义存在差异。
- **当前基础：** DBPrisma 具备完整 SQL Parser；方言转换能力尚未开发。
- **市场工作：** 可以开展客户需求访谈、目标数据库范围收集、典型 SQL 样本归类和未来产品方向评估。
- **当前表达：** “SQL 方言转换是 DBPrisma 可基于现有 SQL 解析能力进一步扩展的方向。”
- **不得表达：** “DBPrisma 已支持 SQL 方言转换”“DBPrisma 可自动完成异构数据库 SQL 转换”。
- **内容优先级：** 作为未来产品方向持续跟踪，不进入当前功能宣传主线。

## 5. 市场优先级建议

建议当前市场传播按以下顺序组织，先围绕已经具备直接产品功能、客户容易理解且容易演示的场景建立认知，再向较复杂的解决方案方向延伸：

| 优先级 | 场景 | 原因 | 当前内容任务 |
| --- | --- | --- | --- |
| P1 | S1 数据库访问安全治理 | 直接对应安全责任和治理需求，核心能力组合清晰 | 安全架构、SQL 防火墙、统一入口 |
| P1 | S2 数据库行为审计与运行分析 | 可通过采集数据直观演示，连接安全、审计和运维价值 | 审计记录、SQL 行为、追溯分析 |
| P1 | S3 数据库连接治理与访问路径统一 | DBA和架构团队容易理解，产品功能可直接演示 | 代理接入、连接池、路由和健康管理 |
| P1 | S4 数据库迁移与渐进式替代 | 市场需求明确，能体现访问路径治理的差异化价值 | 迁移架构、并行验证、访问治理边界 |
| P2 | S6 遗留系统分析、维护与升级改造 | 有较强差异化，需设计可信的 SQL 行为分析演示 | 遗留系统接管、行为观察、分析方法 |
| P2 | S5 异构数据库统一接入与并发访问 | 可面向集团、多数据库环境及集成商 | 统一入口、兼容边界、集成架构 |
| P2 | S8 AI 驱动的数据库治理与软件理解 | 有战略延展性，但需把接口、数据和具体用例讲清楚 | AI 接入架构、数据分析流程、权限边界 |
| P2 | S7 业务孪生与数据访问行为建模 | 战略价值较高，需与业务实体和流程建立关联 | 业务行为数据基础、建模方法 |
| 跟踪 | S9 SQL 方言转换 | 尚未开发，属于独立扩展方向 | 客户需求收集、样本归类、扩展可行性分析 |

优先级是市场内容和客户沟通的先后顺序，不等同于产品研发排期或销售承诺。

## 6. 内容选题的统一结构

每个对外选题必须具备以下信息，避免仅围绕功能名称堆砌文章：

| 字段 | 要回答的问题 |
| --- | --- |
| 目标场景 | 文章或演示解决哪一类客户问题？ |
| 目标角色 | 谁最关心这个问题？谁会推动或批准？ |
| 角色任务 | 该角色需要完成什么工作？ |
| 核心困境 | 当前方式为什么困难？ |
| 失败代价 | 不解决会造成什么业务、技术、安全或管理后果？ |
| 产品切入点 | DBPrisma 哪些能力可以参与解决？ |
| 核心观点 | 这篇内容希望客户记住哪一个判断？ |
| 价值结果 | 客户可以获得什么可理解、可观察的改善？ |
| 证据与演示 | 用什么文档、配置、界面、数据或演示支撑？ |
| 表达状态 | 使用“实现”“支持”“可用于”还是“可扩展”？ |
| 行动引导 | 希望客户进一步交流、提供环境、安排演示还是开展技术评估？ |

**选题合并规则：** 如果两个选题面向相同角色、解决相同任务、核心观点相同，只是功能名称不同，应合并为一篇；如果同一场景下决策者、使用者和集成者的任务不同，则可从不同角色角度分别形成内容，但必须有独立观点，不得重复改写同一段产品介绍。

## 7. 内容生产与证据要求

1. **产品功能内容：** 以能力地图和现行技术资料为基础，展示具体功能、配置或运行结果。
2. **场景解决方案内容：** 可以先于完整标准化交付方案规划，但必须明确使用“支持”“可用于”等表达。
3. **客户案例内容：** 必须有客户授权、事实材料和负责人审批；不得根据测试环境或沟通内容自行写成客户案例。
4. **技术对比内容：** 必须有一致的测试条件和可复核数据；没有原始数据时不作性能优劣判断。
5. **扩展方向内容：** 可以讨论问题、需求和技术方向，不得写成当前产品已实现功能。
6. **SQL 方言转换：** 保留为独立扩展方向，可进行需求调研和未来方案规划；当前不进入 DBPrisma 已实现能力宣传。
7. **最终发布：** 本矩阵不授予 U6 对外发布授权；正式发布仍遵循公司现行口径、证据和审批制度。
