## 一、选题卡

### 角色任务
识别数据库访问链路中的安全控制盲区，评估如何把应用到数据库之间的访问纳入统一治理，并向架构、运维和审计团队说明控制点及责任边界。

### 客户问题
数据库安全配置可能分布在数据库账号权限、应用配置、网络边界、安全设备和日志系统中。安全团队需要回答：访问从哪里进入、由谁发起、经过哪些控制、执行了什么 SQL、最终到达哪个数据库，以及如何追溯相关行为。

### 触发事件
- 数据库访问入口和应用系统数量增加；
- 数据库账号、连接配置分散，安全策略难统一维护；
- 安全检查或内部审计要求梳理数据库访问过程；
- 发生异常访问，需要快速还原来源、SQL 和执行结果；
- 数据库替代或架构调整，需要在既有应用与后端数据库之间增加治理层。

### 核心困境
安全治理关注点容易落在数据库内部权限或网络边界某一侧，而应用与数据库之间的访问链路缺少统一的观察和控制位置。

### 失败代价
访问路径和上下文分散，可能增加策略落地、问题定位、行为追溯和变更管理的工作量。本文不声称必然发生安全事件，也不量化未经验证的损失。

### 核心观点
数据库安全治理不能只看数据库内部，还应把应用到数据库之间的访问路径作为独立治理对象。

### 论证主线
1. 数据库安全控制点并不只存在于数据库内部；
2. 访问路径包含连接入口、客户端身份、访问来源、传输链路、SQL 请求、后端目标和审计记录；
3. 如果这些信息分散在不同系统，统一控制和事后追溯会变得困难；
4. 在数据库前建立统一访问入口，可以把一部分安全控制前移到访问链路；
5. 入口治理不是替代数据库原生权限、网络安全或企业安全体系，而是补充一层可观察、可控制的访问路径；
6. DBPrisma 在现有数据库前提供代理接入，并围绕身份校验、访问控制、SQL 防火墙、行为审计等能力开展治理。

## 二、文章大纲

### 开篇：安全治理的视线是否只停留在数据库内部？
以常见治理关注点切入：账号、权限、补丁、网络边界和日志。指出这些都重要，但还需要回答“访问如何抵达数据库”。

### 第一节：数据库访问路径也是安全边界
定义访问路径：应用连接 → 访问入口 → 身份与来源识别 → 传输链路 → SQL 请求处理 → 后端数据库 → 行为记录。
强调这是分析框架，不代表所有部署拓扑完全相同。

### 第二节：访问路径上需要回答的五个问题
1. 谁在访问：客户端身份与应用层账号；
2. 从哪里访问：来源地址与准入规则；
3. 如何传输：客户端到网关、网关到数据库的链路保护；
4. 执行什么请求：SQL 请求的策略检查与控制；
5. 发生了什么：SQL、身份、来源、目标后端、执行结果等行为记录。

### 第三节：为什么分散的控制点不容易形成治理闭环
围绕策略分散、上下文割裂、审计追溯困难展开。使用“可能”“容易出现”等审慎表达，不把行业观察写成统计事实。

### 第四节：在数据库前建立统一访问入口
说明代理网关的作用与部署逻辑；强调不是把所有安全责任转移给网关，也不替代数据库内部权限体系。

### 第五节：DBPrisma 如何参与访问路径治理
围绕统一接入、身份校验、访问控制、SQL 防火墙、行为审计说明。仅使用正式口径允许的产品事实。不要堆砌所有能力，不加入未经授权案例或性能数据。

### 结尾：从“保护数据库”延伸到“治理数据库访问过程”
给出客户检查清单，形成可执行的下一步。

## 四、事实边界与禁写项

- 不写“覆盖全部数据库安全风险”“完全阻断 SQL 注入”“替代数据库原生安全机制”“替代所有安全产品”。
- 不写表级/列级访问控制、虚拟补丁、QPS、延迟或性能比较数字。
- 不写未经授权的客户案例、测试环境客户背书或行业排名。
- 不写竞品名称。
- 不把 SQL Parser 描述为 SQL 方言转换；本篇无需展开 SQL 方言转换。
- 不把审计数据输出等同于自动满足全部行业合规要求。
- 不把统一访问入口描述为“零配置”或“所有环境无需适配”。
- 不将 TLS、国密配置描述为任何部署条件下均自动启用。
- 不使用“串联安全网关”替代产品全称；正式全称为“息壤数据库串行审计安全网关”。
- 不出现软件著作权审批状态、融资/估值信息或禁用名称。

## 五、审阅重点

### 业务审阅
- “访问路径”是否作为 DBPrisma 的核心市场认知表达；
- 是否清楚区分数据库内部安全与访问链路治理；
- 文章是否先讲客户问题，再讲产品能力；
- 目标角色是否主要面向安全运营，并能被架构、DBA、审计人员理解。

### 技术审阅
- 代理部署与连接地址调整的表述是否准确；
- 身份校验与账号隔离表述是否符合正式口径；
- SQL 防火墙、IP 控制、TLS/国密、审计字段的边界是否准确；
- 是否存在暗示所有访问模式均有相同 SQL 可见性或相同安全处理路径的句子。
