## 1. 建设目标

本体系要解决的不是“持续写文章”这一单点任务，而是建立 DBPrisma 可持续运行的内容生产机制：

1. 对外形成稳定、可识别的产品认知；
2. 从客户场景和角色任务中持续产生有价值的选题；
3. 每项内容都能追溯到产品能力、事实来源和证据；
4. 同一核心内容能够适配不同渠道和载体，减少重复生产；
5. 通过客户反馈、交流和内容表现持续调整选题优先级；
6. 不因内容生产扩大产品承诺，不把规划能力写成当前功能。

## 2. 内容战略判断

### 2.1 核心市场认知

DBPrisma 的内容不应以“我们有多少功能”为起点，而应帮助客户理解：

**数据库访问链路本身需要治理。** 应用与数据库之间的访问过程，涉及连接、身份、流量、SQL、安全策略、审计记录和后端运行状态。若这些要素长期分散在应用、数据库和外围工具中，客户就难以形成统一的控制与观察能力。

DBPrisma 的市场叙事，是围绕数据库访问路径建立统一接入、连接治理、安全防护、流量采集与行为审计能力，并为进一步分析和自动化扩展提供基础。

该叙事是内容组织框架，不意味着 DBPrisma 已覆盖客户全部数据库治理需求，也不代表每个场景都已形成标准化交付包。

### 2.2 产品价值表达主句

建议内部统一采用以下核心表达作为内容母句：

“DBPrisma 部署在现有数据库前端，围绕数据库访问入口提供代理接入、连接治理、安全防护、流量采集与行为审计能力，帮助企业把分散的数据库访问过程纳入统一的治理路径。”

具体内容可根据主题突出其中一组能力，不要求每篇文章重复完整产品介绍。正式对外使用前，仍须与现行权威口径和证据基线核对。

### 2.3 内容差异化原则

内容应体现以下判断，而不是只改写产品功能说明：

- 数据库安全不应只讨论数据库内部权限，还应关注数据库访问路径上的统一控制。
- 数据库审计不应停留在日志汇总，应关注 SQL 与身份、来源、时间、目标后端和执行结果之间的关联。
- 数据库连接不应完全分散在应用中，应成为可以统一管理和观察的基础设施对象。
- 数据库迁移不只是数据搬运，还需要管理迁移期间的访问路径和数据库流量。
- SQL 解析是理解 SQL 的基础能力，但不等同于 SQL 方言转换。
- AI 相关内容应从 SQL 与访问行为数据、接口、分析流程和治理边界切入，不宣传尚未形成的自治运维能力。

## 3. 内容架构：五层资产模型

| 层级 | 资产类型 | 作用 | 典型产出 |
| --- | --- | --- | --- |
| L1 | 核心叙事 | 建立长期稳定的产品认知和表达框架 | 产品定位、核心观点、标准介绍 |
| L2 | 主题系列 | 按客户问题组织内容，形成连续主题 | 安全治理、行为审计、连接治理、数据库迁移系列 |
| L3 | 具体选题 | 将主题转化为面向特定角色的独立观点 | 文章选题卡、技术问题、场景观点 |
| L4 | 内容成品 | 对选题进行完整论证和事实呈现 | 技术文章、场景方案、白皮书章节、演示脚本、图解 |
| L5 | 渠道版本 | 根据载体和阅读情境进行剪裁 | 官网版、公众号版、销售材料、会议演示、短内容 |

层级关系：L1 约束 L2；L2 组织 L3；L3 驱动 L4；L4 经适配形成 L5。渠道不反向决定产品事实，也不应各自建立互相冲突的产品定位。

## 4. 主题体系与优先级

### 4.1 P1：当前主传播主题

| 主题编号 | 主题 | 核心客户问题 | 主要角色 | 产品切入点 |
| --- | --- | --- | --- | --- |
| T1 | 数据库访问安全治理 | 如何在数据库访问路径上建立统一安全控制 | R4 安全运营；协同 R1/R2/R3/R8 | 代理入口、身份校验、IP 控制、TLS/国密、SQL 防火墙、审计 |
| T2 | 数据库行为审计与运行分析 | 如何还原谁在何时从哪里对哪个数据库执行了什么操作 | R8 审计、R4 安全；协同 R3/R2/R7/R5 | SQL 采集、身份来源、执行结果与耗时、脱敏、结构化输出 |
| T3 | 数据库连接治理与访问路径统一 | 如何管理分散在多个应用中的数据库连接及后端访问路径 | R3 DBA；协同 R2/R7/R5 | 代理接入、连接池、多路复用、读写分离、负载分配、健康管理 |
| T4 | 数据库并行验证与渐进式替代 | 在应用驱动/连接协议及目标数据库 SQL/行为兼容条件满足时，如何组织并行验证与访问切换 | R2 架构负责人；协同 R1/R3/R5/R9/R10 | A 统一接入、B 多后端路由、D 流量采集审计；兼容性评估和 PoC 前置，写广播不作为默认前提 |

### 4.2 P2：延展主题

| 主题编号 | 主题 | 当前内容定位 | 注意事项 |
| --- | --- | --- | --- |
| T5 | 遗留系统分析、维护与升级改造 | 从真实 SQL 访问行为理解系统的数据访问路径 | 不承诺自动还原全部业务逻辑或源代码 |
| T6 | 数据库多实例接入与治理 | 当前聚焦多个同类 MySQL 或 PG 实例的统一接入与访问治理；跨数据库类型统一接入作为未来扩展方向 | 同类实例须核验协议/驱动与版本兼容；一个网关统一代理多种数据库类型尚未实现 |
| T7 | AI 驱动的数据库治理与软件理解 | 讨论 SQL/行为数据进入 AI 分析和治理流程 | 区分接口基础、可支持场景和具体已交付能力 |
| T8 | 业务孪生与数据访问行为建模 | 讨论数据库访问行为作为业务过程观测数据的价值 | DBPrisma 是数据采集与分析基础，不是完整业务孪生平台 |

### 4.3 持续跟踪的独立扩展方向

**T9：SQL 方言转换。** 当前未开发，只能作为独立可扩展方向开展客户需求访谈、目标数据库范围收集、SQL 样本归类和未来方向评估。不得并入 SQL Parser 的已实现能力，不得写成当前产品功能或支持承诺。

## 5. 内容类型与标准结构

内容类型不是渠道类型。每一篇内容先确定其要完成的沟通任务，再决定采用文章、方案、图解或演示等载体。

| 内容类型 | 主要任务 | 标准结构 |
| --- | --- | --- |
| 观点/认知型 | 建立客户对问题的正确认识 | 现实问题 → 常见误区 → 核心判断 → 方法框架 → 产品切入点 |
| 技术解释型 | 解释一项技术机制及其价值 | 技术背景 → 工作机制 → 关键边界 → 适用条件 → 产品实现 |
| 场景方案型 | 说明如何处理一个客户场景 | 场景现状 → 角色任务 → 目标架构 → 实施步骤 → 风险边界 → 产品能力 |
| 产品能力型 | 解释一项或一组已实现能力 | 客户问题 → 功能机制 → 配置/运行证据 → 适用边界 → 价值 |
| 实践/案例型 | 证明某种方法在真实环境中的效果 | 客户背景 → 问题 → 方案 → 实施过程 → 结果 → 授权与证据 |
| 演示型 | 让客户直观看到能力和工作过程 | 演示目标 → 环境与前提 → 操作步骤 → 观察点 → 结果 → 限制说明 |

案例内容必须有客户授权和可核验材料。测试环境、内部验证和交流信息不得自动写成客户案例。

## 6. 选题立项规则

每个选题建立独立选题卡，至少包括：

1. 选题编号、标题和主题编号；
2. 目标场景及矩阵场景编号；
3. 目标角色及其具体任务；
4. 客户问题、触发事件和失败代价；
5. 核心观点（一句话，必须是可讨论的判断，而非功能名称）；
6. 产品切入点及能力地图对应项；
7. 计划使用的事实、证据和演示材料；
8. 表达状态：已实现、支持、可用于、可扩展或规划；
9. 内容类型、拟用载体和行动引导；
10. 审核状态、发布状态和效果反馈。

### 6.1 选题质量门槛

满足以下条件才进入正式生产：

- 面向一个明确的主要角色；
- 对应一个真实、具体的任务或问题；
- 有一个独立核心观点；
- 与已有选题不构成简单重复；
- 产品切入点与事实状态准确；
- 有证据路径，或明确标记为观点性内容；
- 有清晰的读者下一步行动。

### 6.2 合并与拆分规则

同一角色、同一任务、同一核心观点，仅功能名称不同的选题合并。一个场景中不同角色承担不同任务，且核心观点不同，可以拆分为不同选题。不得为了增加数量，把同一观点改写成多篇近似文章。

## 7. 内容生产工作流

| 阶段 | 工作 | 主要检查点 | 输出 |
| --- | --- | --- | --- |
| 1. 选题 | 从场景—角色—价值矩阵提取客户问题 | 角色、任务、观点是否明确 | 选题卡 |
| 2. 事实映射 | 关联能力地图、口径、术语、证据 | 能力状态、名称、适用边界 | 事实与证据清单 |
| 3. 内容设计 | 确定论证结构、内容类型和载体 | 是否先讲问题和观点，避免功能堆砌 | 内容大纲 |
| 4. 初稿生产 | 完成主体内容和必要图表/演示 | 逻辑、准确性、可读性 | 内容初稿 |
| 5. 事实审核 | 核对产品事实、技术边界、证据 | 不夸大、不推断、不混淆规划和现状 | 事实审核记录 |
| 6. 业务审核 | 核对市场价值、目标客户和行动引导 | 是否解决真实客户问题 | 业务审核记录 |
| 7. 发布审批 | 按公司现行制度执行审批 | 权威口径、证据、U6 授权 | 可发布版本 |
| 8. 渠道适配 | 从审核通过的核心内容生成渠道版本 | 不改变事实和核心观点 | 渠道版本 |
| 9. 反馈迭代 | 汇总客户提问、线索、阅读和演示反馈 | 哪些观点有效、哪些需要修订 | 选题反馈和版本更新 |

市场内容规划不必等待全部技术细节确认后才开始；但涉及具体实现、兼容范围、部署条件、性能或客户结果的主张，必须按证据要求核验。技术确认、业务审核和发布授权是不同环节。

## 8. 事实、证据与表达治理

### 8.1 事实来源优先级

1. 公司现行权威对外口径；
2. 产品事实基线、正式术语、名称映射和禁写清单；
3. 已登记且可核验的产品证据；
4. 产品能力地图及场景—角色—价值矩阵（作为内部分析依据）；
5. 技术手册、配置参考、测试记录和技术人员确认；
6. 负责人明确提供且尚未进入正式资料的事实（按内部事实输入管理，必要时补证）。

来源冲突时，不得由内容撰写者自行选择有利表述，应记录冲突并提交负责人裁定。对外发布仍以公司正式口径和审批为准。

### 8.2 动词与能力状态

- “实现/具备”：用于已确认实现的具体产品能力。
- “支持”：用于产品可承载的能力或技术范围，不自动代表客户场景已交付。
- “可用于”：用于说明能力与场景之间的合理应用关系。
- “可扩展”：用于尚未开发或尚未形成现有产品能力的未来方向。
- “规划/探索”：仅用于内部路线和研究讨论。

不得把“有技术基础”推导成“功能已实现”，不得把“支持场景”推导成“已有客户成功案例”。

### 8.3 特别控制项

- SQL Parser 与 SQL 方言转换必须分开；方言转换为未开发的独立扩展方向。
- 统一接入不等于 SQL 方言统一或自动转换。
- 多后端写广播不等于数据库复制完成或迁移完成。
- 审计数据输出不等于自动满足全部行业合规要求。
- SQL/行为数据可用于 AI 分析，不等于已具备完全自治运维。
- 不得未经证据支持写入性能数字、客户案例、兼容范围、认证结论和客户效果。
- 遵守现行禁写清单、产品名称映射和证书原文要求。
- 本体系不修改正式对外口径、术语台账、禁写清单、证据登记或 U6 授权状态。

## 9. 内容资产组织建议

建议在分析文件中独立维护内容体系，不与对外成稿混放：

`公司文档/分析文件/DBPrisma/02-内容体系/`

建议结构：

- `00-内容体系建设方案-V1.0.md`：本文件，维护战略、规则和流程；
- `01-主题与选题库-V1.0.md`：主题、选题卡及状态；
- `02-内容模板/`：选题卡、内容大纲、事实证据清单、审核记录模板；
- `03-内容成品/`：经选题立项的内容初稿和审核稿；
- `04-渠道版本/`：由核心内容适配的不同渠道版本；
- `05-反馈与复盘/`：客户反馈、内容效果和选题调整记录。

内容成品必须保留选题编号和上游事实/证据引用。渠道版本必须指向唯一的核心内容，不应成为独立事实源。

## 10. 运行指标

不以发文数量作为唯一目标。建议按四类指标观察：

- 资产建设：有效选题数、完成内容数、可复用内容比例、证据关联率；
- 触达与互动：目标角色触达、有效阅读、收藏/转发、技术交流请求；
- 市场转化：客户咨询、演示申请、技术交流、测试环境验证和商机推进；
- 内容质量：事实问题数、返工率、重复选题比例、客户理解偏差。

现阶段不设未经数据验证的数值目标。先建立基线，再根据实际渠道和销售反馈设定目标。

## 11. 第一轮执行建议

第一轮只推进 P1 四个主题，不同时铺开全部 P2：

1. 建立 T1—T4 主题选题卡；
2. 每个主题先形成 3—5 个候选选题；
3. 进行去重、角色任务校验和证据映射；
4. 从中选择最有证据、最容易演示、最接近客户决策问题的选题进入初稿；
5. 先形成一个完整的核心内容，再验证其能否拆分为技术文章、场景方案、演示脚本和渠道短版。

第一轮不以“凑齐文章数量”为目标，而以验证内容方法是否有效、事实治理是否可执行、跨渠道复用是否成立为目标。
