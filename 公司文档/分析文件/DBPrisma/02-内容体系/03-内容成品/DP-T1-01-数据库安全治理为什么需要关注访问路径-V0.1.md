# 数据库安全治理，为什么需要关注访问路径

> 文章定位：观点/认知型  
> 选题编号：DP-T1-01  
> 版本：V0.1 初稿  
> 状态：内部审阅稿，未经发布审批

数据库安全建设通常会涉及账号权限、网络边界、加密传输、漏洞管理和审计日志。这些工作都很重要。但在实际治理中，还有一个容易被忽略的对象：**应用与数据库之间的访问路径。**

数据库并不是孤立运行的。业务应用通过连接访问数据库，请求经过网络和连接入口，携带身份信息与 SQL 操作，最终到达具体的数据库服务。一次数据库访问从哪里发起、由谁发起、经过什么控制、执行了什么操作、结果如何，构成了完整的访问过程。

如果安全治理只关注数据库内部配置，而没有把这条访问路径纳入整体视野，就可能难以回答一些基础问题：哪些应用正在访问数据库？访问来自哪里？身份如何识别？SQL 请求是否经过策略检查？出现异常后，能否把请求与访问来源、目标数据库和执行结果关联起来？

因此，数据库安全治理不仅要保护数据库本身，也需要治理通往数据库的访问路径。

## 一、数据库访问路径也是安全治理对象

从应用到数据库的一次访问，通常会涉及多个环节：

- **应用连接：** 业务系统通过连接配置访问数据库；
- **访问入口：** 连接进入网络或数据库访问链路；
- **身份与来源：** 系统识别访问主体及其来源；
- **传输链路：** 请求在客户端、访问入口和数据库之间传输；
- **SQL 请求：** 数据库接收并执行查询、写入或其他操作；
- **行为记录：** 相关访问信息被记录，用于审计和后续分析。

这些环节共同构成数据库访问路径。它不只是网络拓扑，也不仅是一条 TCP 连接，而是身份、来源、请求、控制策略和行为记录共同组成的访问过程。

从安全治理角度看，至少需要回答五个问题：

1. **谁在访问？** 是哪个应用或客户端，使用什么身份发起连接？
2. **从哪里访问？** 访问来自什么地址，是否符合准入规则？
3. **如何传输？** 客户端到访问入口、访问入口到数据库之间，是否采用符合要求的链路保护方式？
4. **执行什么请求？** SQL 请求是否需要经过规则检查，哪些请求应被放行、记录或拦截？
5. **发生了什么？** 请求最终到达哪个数据库，执行结果如何，相关行为能否追溯？

这五个问题并不意味着所有安全控制都必须由一个组件完成。数据库自身的账号权限、网络安全设备、身份管理系统和企业安全运营平台仍然各有职责。关键在于，数据库访问路径需要有明确的治理位置和可观察的数据。

## 二、为什么分散的控制点不容易形成治理闭环

在一些系统环境中，数据库连接配置由不同业务应用分别维护，身份和权限信息分布在应用与数据库侧，网络访问策略由其他系统管理，审计记录又进入不同日志平台。

这种分散方式并不必然意味着不安全，但会增加统一治理的难度。

**首先，策略可能分散在不同位置。** 应用连接、网络准入、数据库账号和 SQL 规则分别由不同系统管理。策略制定者需要了解各处配置，变更时也需要协调多个环节。

**其次，访问上下文容易割裂。** 单独看到一条 SQL，未必能够完整理解它由哪个应用或客户端发起、来自什么位置、经过何种控制，以及最终到达哪个后端数据库。不同系统中的记录如果缺少关联，调查人员就需要额外进行信息拼接。

**再次，事后审计依赖多个数据来源。** 当需要调查异常访问或还原数据库操作过程时，安全人员可能需要分别查询应用日志、网络记录、数据库日志和其他审计系统。记录格式、时间和身份标识不一致，也会增加分析工作。

问题的关键并不是某一种日志或某一个安全设备是否足够强，而是数据库访问过程是否能够在适当的位置被统一观察和治理。

## 三、在数据库前建立统一访问入口

一种可行的治理思路，是在业务应用与现有数据库之间建立统一的数据库访问入口。

应用不再分别直接连接各个数据库地址，而是通过访问入口进入后端数据库。这样，数据库访问链路上就形成了一个可以实施连接管理、安全控制和行为采集的位置。

~~~text
业务应用 / 客户端
        |
        | 数据库连接
        v
数据库访问入口
        |
        +-- 身份校验与访问来源控制
        |
        +-- SQL 请求策略检查
        |
        +-- 访问行为采集与审计
        |
        v
现有数据库服务
~~~

这一架构的意义，不是把数据库原有安全机制全部移走，也不是让访问入口承担所有安全责任，而是在数据库前增加一层面向访问过程的治理能力。

数据库原生权限仍然负责数据库内部的权限管理；网络安全体系继续负责相应的网络边界和基础设施安全；企业身份管理和安全运营体系仍然承担各自职责。统一访问入口补充的是数据库访问链路上的集中控制与观察能力。

## 四、DBPrisma 如何参与数据库访问路径治理

DBPrisma（息壤数据库串行审计安全网关）部署在现有数据库前，为数据库访问过程提供代理接入和安全治理能力。

在接入方式上，企业无需修改原有业务应用代码，只需将数据库连接地址指向 DBPrisma，即可完成网关接入。通过这一入口，DBPrisma 可接管客户端身份校验，实现应用层账号与数据库底层账号的物理隔离。

在访问控制方面，DBPrisma 提供访问控制和 SQL 防火墙能力，可在数据库访问入口对 SQL 请求实施规则检查，并按策略进行处理。结合访问来源控制，可以把部分安全策略放在数据库访问路径上实施。

在链路保护方面，DBPrisma 支持数据库链路国密加密。具体部署时，客户端到网关、网关到数据库两段链路可以根据实际环境进行配置。

在行为审计方面，DBPrisma 提供数据库行为审计能力，对经过网关的数据库访问过程进行采集和记录，为后续审计、调查和运行分析提供数据基础。

这些能力共同构成 DBPrisma 在数据库访问路径上的产品价值：不仅提供一个数据库代理入口，也将身份校验、访问控制、SQL 防护和行为审计纳入同一治理路径。

需要说明的是，访问入口治理并不意味着能够覆盖所有数据库安全风险，也不替代数据库自身权限管理、网络安全体系和企业现有安全运营制度。具体能力范围还需要结合产品版本、接入模式和部署环境确定。

## 五、从保护数据库到治理数据库访问过程

数据库安全建设需要关注的不只是数据库内部“设置了什么”，还需要理解访问过程“实际发生了什么”。

企业可以从以下问题开始检查现有数据库访问治理：

- 是否清楚掌握各业务应用访问数据库的入口和连接路径？
- 是否能够识别访问主体及其来源，并明确身份校验责任？
- 是否能够对数据库访问请求实施适当的策略检查？
- 是否能够对访问链路进行符合要求的加密保护？
- 是否能够将 SQL 请求与身份、来源、目标数据库和执行结果关联起来？
- 发生异常访问时，是否有明确的记录和追溯路径？

如果这些问题尚未形成统一答案，就有必要把数据库访问路径纳入安全治理规划。

**数据库安全治理的视线，应从数据库内部延伸到数据库访问过程。** 通过在现有数据库前建立统一访问入口，企业可以为访问控制、SQL 防护和行为审计提供一个集中的实施位置。DBPrisma 正是围绕这一访问路径提供代理接入、安全防护与行为审计能力。
