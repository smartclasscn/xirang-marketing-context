# 数据库迁移不只是数据搬运，还要管理访问路径

> 修订版本：V0.2（2026-11-22）
> 核心调整：将协议/驱动兼容与 SQL/数据库行为兼容作为两项独立前提；以兼容条件满足后的并行验证为主场景。

> 文章定位：观点/认知型 + 场景方案型  
> 选题编号：DP-T4-01  
> 版本：V0.1 初稿  
> 状态：内部审阅稿，未经发布审批

数据库迁移项目通常首先关注数据本身：如何完成结构转换、数据搬运、校验和切换。但在讨论访问路径之前，还需要先回答两个不同的兼容性问题：应用使用的驱动和连接协议能否通过目标接入层到达目标数据库；目标数据库能否正确执行应用实际使用的 SQL，并保持必要的数据库行为。但在真实业务系统中，数据库并不是独立存在的。应用持续通过连接访问数据库，后台任务、报表程序、批处理和其他服务也可能依赖原有数据库地址和访问行为。

只有在连接协议/驱动适配与 SQL/数据库行为兼容性得到验证后，才适合进一步设计迁移期间的统一接入、后端路由、并行验证和切换回退。因此，迁移项目面对的不只是“数据如何从旧库进入新库”，还包括“应用能否通过现有驱动连接目标路径、迁移期间访问流量如何组织、切换时连接如何调整，以及出现问题时如何恢复原有访问路径”。

**数据库迁移不仅是数据搬运过程，也是数据库访问路径的调整过程。**

## 一、先区分两层兼容性：连接协议与 SQL/数据库行为

数据库迁移中的“兼容”不是单一概念，至少要拆成两个层面。

**第一层是连接协议和驱动兼容。** 应用使用什么数据库驱动、通过什么连接协议建立会话，决定了代理或网关能否承接应用连接。DBPrisma 当前已知的产品适配方向是 MySQL 与 PG，分别由对应产品适配。目标数据库即使提供 Oracle 兼容 SQL 或兼容模式，也不能据此推断 DBPrisma 已支持 Oracle 驱动和 Oracle 连接协议。协议不匹配时，不能直接把 DBPrisma 放在应用和目标数据库之间并假设连接可用。

**第二层是 SQL 与数据库行为兼容。** 即使应用连接能够建立，目标数据库仍需正确处理应用实际使用的 SQL、数据类型、函数、事务、会话状态及相关行为。语法能够解析，不代表执行结果和业务语义一定一致。

因此，迁移前的兼容性评估和 PoC 应分别验证这两个层面。本文讨论的 DBPrisma 访问路径治理，前提是应用连接协议处于对应产品适配范围内，且目标数据库对应用 SQL 与必要数据库行为具有足够兼容性。

## 二、把迁移过程拆成数据路径和访问路径

迁移项目至少包含两个相互关联、但不能混为一谈的工作面。

**数据路径**关注数据如何从源端到达目标端，包括结构处理、数据复制、校验、增量同步和一致性确认等工作。

**访问路径**关注业务应用如何连接数据库，包括连接入口、身份、请求流量、后端目标、访问策略和切换过程。

二者需要协同，但完成其中一项并不代表另一项自动完成。例如，数据已经复制到目标库，并不能证明所有应用都已切换；应用连接已经指向目标库，也不能证明目标库的数据完整性和业务一致性已经验证。

~~~text
                 +--> 旧数据库
业务应用 --> 访问入口
                 +--> 新数据库
~~~

当旧库和新库并行存在时，访问入口可以成为组织应用访问关系和后端路由的一个位置。具体由哪些应用访问哪个后端、是否允许并行写入、如何处理事务和一致性，必须由迁移方案明确，不能仅凭存在统一入口就自动解决。这里的“并行验证”首先可以是受控地将不同应用或测试流量路由到不同后端，并观察执行行为；它不自动意味着生产双写或数据同步。

## 三、为什么需要先理解真实访问行为

迁移方案经常依据已有系统文档、数据库对象清单和开发团队提供的信息制定。但随着系统运行时间增长，文档可能与实际访问情况存在差异。

在迁移前观察真实 SQL 和访问行为，可以帮助项目团队回答：哪些应用或客户端正在访问数据库？常见 SQL 类型和访问模式是什么？哪些访问路径仍然活跃？是否存在未纳入迁移计划的程序或批处理？哪些 SQL 和访问行为需要在目标数据库上重点验证？

这些观察结果可以帮助完善迁移测试范围，但不能替代 SQL 兼容性测试、数据一致性验证和业务验收。尤其是不同数据库之间的语法、函数、类型和事务语义差异，需要单独评估。

SQL 解析相关基础能力不等于 SQL 方言转换能力。大多数可识别的兼容差异应优先通过迁移前的兼容性评估、PoC、目标数据库适配或应用调整解决。若仍存在无法通过这些方式解决的 SQL 语法或语义差异，AST 处理、语义识别和 SQL 方言转换可以作为独立技术方向评估；SQL 方言转换本身仍未开发，不能把现有解析基础直接视为已完成跨数据库转换。

## 四、统一访问入口可以参与迁移过程，但不是迁移工具

在应用和数据库之间建立代理入口，可以为迁移期间的访问路径管理提供一个集中位置。

如果应用连接协议与 DBPrisma 当前产品适配范围匹配，且目标数据库已通过 SQL/行为兼容性验证，应用即可按项目方案接入统一入口。后端数据库访问关系可以在代理层按已配置的规则组织，项目团队可以围绕入口规划应用接入、后端目标和流量观察。

DBPrisma 作为数据库代理网关，提供代理接入、连接治理、数据路由和行为审计等能力。在应用驱动/连接协议适配、目标数据库 SQL/行为兼容等前提满足时，可以参与数据库迁移期间的访问路径组织。

例如，在迁移验证阶段，项目团队可以结合实际环境，规划不同应用或测试流量访问相应后端，并通过访问行为采集了解实际请求情况。DBPrisma 的多后端路由可以作为访问组织手段。写广播不是并行验证的默认前提；若项目确实需要，应先专项验证广播范围、事务边界、失败处理和数据一致性责任。

需要明确的是，DBPrisma 不应被描述为完整的数据迁移工具。它不能仅凭代理接入就替代数据抽取、数据复制、结构转换、数据校验、增量同步和业务一致性验证。它所参与的是数据库访问路径及相关流量的治理。

## 五、迁移切换前，先把访问路径验证清楚

迁移项目可以把访问路径检查纳入切换准备：

1. **建立应用清单。** 明确哪些应用、批处理、报表和运维程序访问目标数据库。
2. **梳理连接关系。** 记录连接地址、使用账号、驱动、连接池和访问来源。
3. **区分数据验证与访问验证。** 数据正确不等于连接路径正确，连接成功也不等于业务数据一致。
4. **验证路由规则。** 明确每类应用或流量访问哪个后端，以及规则生效条件。
5. **验证事务与会话行为。** 对关键业务操作、长事务、批处理和会话状态进行专项测试。
6. **设计切换与回退。** 明确切换触发条件、观察指标、责任人和恢复原路径的步骤。
7. **保留审计线索。** 在授权和适用范围内采集访问行为，为问题定位提供依据。

迁移切换不应只以“目标库已经可用”为判断条件，还应确认应用驱动和连接协议适配、SQL 与数据库行为兼容、应用访问、路由规则、数据验证、业务验收和回退安排均符合项目要求。

## 六、让数据迁移和访问路径治理协同推进

数据库迁移是一项涉及数据、应用、数据库和运维流程的系统工程。数据迁移工具解决数据如何移动和校验的问题；应用改造解决业务如何适配目标数据库的问题；访问治理则关注应用如何连接、流量如何组织以及切换过程如何观察。

**把访问路径纳入迁移设计，可以让项目团队更早识别应用连接关系和切换风险。** DBPrisma 通过代理接入、连接治理、数据路由和行为审计，为迁移期间的数据库访问路径管理提供一种技术支撑。但迁移是否成功，仍取决于连接协议适配、SQL 与数据库行为兼容、数据完整性、业务功能、性能和切换回退等各项验证共同完成。
