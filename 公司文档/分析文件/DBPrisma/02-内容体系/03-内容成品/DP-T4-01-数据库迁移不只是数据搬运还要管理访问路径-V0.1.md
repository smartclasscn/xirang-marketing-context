# 数据库迁移不只是数据搬运，还要管理访问路径

> 文章定位：观点/认知型 + 场景方案型  
> 选题编号：DP-T4-01  
> 版本：V0.1 初稿  
> 状态：内部审阅稿，未经发布审批

数据库迁移项目通常首先关注数据本身：如何完成结构转换、数据搬运、校验和切换。但在真实业务系统中，数据库并不是独立存在的。应用持续通过连接访问数据库，后台任务、报表程序、批处理和其他服务也可能依赖原有数据库地址和访问行为。

因此，迁移项目面对的不只是“数据如何从旧库进入新库”，还包括“迁移期间应用如何访问数据库、访问流量如何组织、切换时连接如何调整，以及出现问题时如何恢复原有访问路径”。

**数据库迁移不仅是数据搬运过程，也是数据库访问路径的调整过程。**

## 一、迁移期间，应用访问关系并不会自动消失

数据库迁移往往需要经历准备、验证、并行运行、切换和观察等环节。不同项目的实施顺序和持续时间不同，但在多数渐进式迁移场景中，旧数据库和新数据库可能在一段时间内同时存在。

这段时间内，企业需要回答一些访问层面的问题：哪些应用仍然访问旧数据库，哪些应用开始访问新数据库？应用连接地址是否需要逐个调整？测试流量和生产流量如何区分？多个后端同时存在时，访问请求应如何路由？切换后如何观察应用访问是否符合预期？出现问题时，如何停止新路径并恢复原有连接？

如果项目只关注数据迁移工具的执行结果，而没有同步梳理应用访问关系，就可能出现数据已经准备好、应用连接却尚未完成切换，或者部分应用仍然访问旧后端的情况。

## 二、把迁移过程拆成数据路径和访问路径

迁移项目至少包含两个相互关联、但不能混为一谈的工作面。

**数据路径**关注数据如何从源端到达目标端，包括结构处理、数据复制、校验、增量同步和一致性确认等工作。

**访问路径**关注业务应用如何连接数据库，包括连接入口、身份、请求流量、后端目标、访问策略和切换过程。

二者需要协同，但完成其中一项并不代表另一项自动完成。例如，数据已经复制到目标库，并不能证明所有应用都已切换；应用连接已经指向目标库，也不能证明目标库的数据完整性和业务一致性已经验证。

~~~text
                 +--> 旧数据库
业务应用 --> 访问入口
                 +--> 新数据库
~~~

当旧库和新库并行存在时，访问入口可以成为组织应用访问关系和后端路由的一个位置。具体由哪些应用访问哪个后端、是否允许并行写入、如何处理事务和一致性，必须由迁移方案明确，不能仅凭存在统一入口就自动解决。

## 三、为什么需要先理解真实访问行为

迁移方案经常依据已有系统文档、数据库对象清单和开发团队提供的信息制定。但随着系统运行时间增长，文档可能与实际访问情况存在差异。

在迁移前观察真实 SQL 和访问行为，可以帮助项目团队回答：哪些应用或客户端正在访问数据库？常见 SQL 类型和访问模式是什么？哪些访问路径仍然活跃？是否存在未纳入迁移计划的程序或批处理？哪些 SQL 和访问行为需要在目标数据库上重点验证？

这些观察结果可以帮助完善迁移测试范围，但不能替代 SQL 兼容性测试、数据一致性验证和业务验收。尤其是不同数据库之间的语法、函数、类型和事务语义差异，需要单独评估。

SQL Parser 可以帮助识别和理解 SQL 结构，但 SQL 解析能力不等于 SQL 方言转换能力。SQL 方言转换是独立的复杂能力，不能把解析结果直接视为已完成跨数据库转换。

## 四、统一访问入口可以参与迁移过程，但不是迁移工具

在应用和数据库之间建立代理入口，可以为迁移期间的访问路径管理提供一个集中位置。

如果应用连接到统一入口，后端数据库访问关系可以在代理层按已配置的规则组织。这样，项目团队可以围绕入口规划应用接入、后端目标和流量观察，而不必把所有后端关系都分散在每个应用配置中。

DBPrisma 作为数据库代理网关，提供代理接入、连接治理、数据路由和行为审计等能力，可以参与数据库迁移期间的访问路径组织。

例如，在迁移验证阶段，项目团队可以结合实际环境，规划不同应用或测试流量访问相应后端，并通过访问行为采集了解实际请求情况。若涉及多后端路由、写广播或故障处理，应逐项确认其规则、事务边界和失败语义。

需要明确的是，DBPrisma 不应被描述为完整的数据迁移工具。它不能仅凭代理接入就替代数据抽取、数据复制、结构转换、数据校验、增量同步和业务一致性验证。它所参与的是数据库访问路径及相关流量的治理。

## 五、迁移切换前，先把访问路径验证清楚

迁移项目可以把访问路径检查纳入切换准备：

1. **建立应用清单。** 明确哪些应用、批处理、报表和运维程序访问目标数据库。
2. **梳理连接关系。** 记录连接地址、使用账号、驱动、连接池和访问来源。
3. **区分数据验证与访问验证。** 数据正确不等于连接路径正确，连接成功也不等于业务数据一致。
4. **验证路由规则。** 明确每类应用或流量访问哪个后端，以及规则生效条件。
5. **验证事务与会话行为。** 对关键业务操作、长事务、批处理和会话状态进行专项测试。
6. **设计切换与回退。** 明确切换触发条件、观察指标、责任人和恢复原路径的步骤。
7. **保留审计线索。** 在授权和适用范围内采集访问行为，为问题定位提供依据。

迁移切换不应只以“目标库已经可用”为判断条件，还应确认应用访问、路由规则、业务验证和回退安排均符合项目要求。

## 六、让数据迁移和访问路径治理协同推进

数据库迁移是一项涉及数据、应用、数据库和运维流程的系统工程。数据迁移工具解决数据如何移动和校验的问题；应用改造解决业务如何适配目标数据库的问题；访问治理则关注应用如何连接、流量如何组织以及切换过程如何观察。

**把访问路径纳入迁移设计，可以让项目团队更早识别应用连接关系和切换风险。** DBPrisma 通过代理接入、连接治理、数据路由和行为审计，为迁移期间的数据库访问路径管理提供一种技术支撑。但迁移是否成功，仍取决于数据、SQL 兼容、业务功能、性能和切换回退等各项验证共同完成。
