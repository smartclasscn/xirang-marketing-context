# 数据库审计不应只记录 SQL：还需要回答谁、何时、从哪里

> 文章定位：观点/认知型 + 技术解释型  
> 选题编号：DP-T2-01  
> 版本：V0.1 初稿  
> 状态：内部审阅稿，未经发布审批

数据库审计常常从 SQL 记录开始。系统记录了执行语句、执行时间和返回状态，似乎已经留下了数据库操作的痕迹。但当安全人员需要调查一次异常访问，或者审计人员需要解释一项数据库操作时，仅有 SQL 往往还不够。

一条 SQL 能说明数据库收到过什么请求，却未必能独立回答：请求由谁发起？来自哪个应用或客户端？发生在什么时间？访问了哪个后端数据库？最终执行成功还是失败？

**数据库审计的目标不应只是保存 SQL 文本，而应尽可能还原一次数据库访问行为。**

## 一、SQL 是审计的重要内容，但不是全部上下文

SQL 是数据库操作最直接的表达。查询、插入、更新、删除以及管理操作，都会通过相应请求进入数据库执行过程。因此，SQL 语句本身是数据库审计的重要对象。

但在实际调查中，审计人员通常还需要理解 SQL 周围的上下文。例如，这条语句由哪个客户端或应用连接发起？连接使用的身份是什么？请求来自什么网络地址或访问来源？请求发生在什么时间？请求被路由到哪个数据库后端？最终执行成功、失败，还是在执行过程中发生了其他结果？

这些信息决定了审计记录能否从“发生过一条 SQL”进一步支持“某个访问主体在特定时间通过某条访问路径，对某个数据库发起了某项操作”的判断。

这里必须区分应用账号与实际操作人。应用连接可能使用共享服务账号，网关或数据库看到的身份也可能是应用账号。审计系统必须如实记录其能够识别和采集的身份信息，不能把应用账号直接等同于实际操作的自然人。

## 二、缺少上下文，审计调查就容易变成信息拼接

当 SQL 日志、应用日志、网络访问记录和数据库运行日志分散在不同系统中时，调查人员往往需要先确定关联线索，再逐项查找记录。

**身份线索可能不连续。** 应用日志可能记录业务用户，数据库日志记录数据库账号，网络设备记录源地址。若缺少稳定的关联标识，就难以直接判断这些记录是否对应同一次访问。

**时间线需要人工还原。** 不同系统的记录可能采用不同时间精度、时区或时间同步条件。调查人员需要先校准时间，再判断请求经过各个环节的先后关系。

**目标对象可能不够明确。** 在存在多个数据库实例或多个后端的环境中，只记录 SQL 而没有目标后端信息，会增加确认操作对象的难度。

**执行结果容易被忽略。** 请求被发出不代表请求成功执行。审计分析需要区分请求、执行和结果，避免把“尝试访问”写成“成功操作”。

问题并不是必须由一个系统替代所有日志平台。更现实的做法，是在数据库访问链路的适当位置采集能够稳定获得的上下文信息，并通过明确字段和关联标识，为后续集中分析提供基础。

## 三、从 SQL 日志走向访问行为记录

可以把一次数据库访问理解为一个由多个要素构成的事件：

| 观察维度 | 需要回答的问题 | 可能的记录内容 |
| --- | --- | --- |
| 时间 | 何时发生？ | 请求或执行时间 |
| 身份 | 使用什么身份？ | 客户端身份、应用账号或数据库账号 |
| 来源 | 从哪里发起？ | 来源地址或连接来源信息 |
| 请求 | 执行了什么？ | SQL 文本或经处理的 SQL 信息 |
| 目标 | 访问哪个对象？ | 后端数据库或目标实例 |
| 结果 | 最终发生什么？ | 执行状态或结果信息 |

这是一种审计分析框架，不代表每个产品、每种协议或每个输出接口都必然提供全部字段。具体可采集内容取决于接入方式、数据库协议、产品版本和部署配置。

需要区分三个层次：记录 SQL；将 SQL 与可识别的身份、来源、时间和目标信息关联；基于记录开展检索、关联、统计和调查。具备第一层，不意味着自动具备后两层。只有把数据范围、字段定义、关联方式和使用流程讲清楚，审计记录才可能真正服务于治理工作。

## 四、DBPrisma 如何为数据库行为审计提供数据基础

DBPrisma 部署在现有数据库前，通过代理接入数据库访问链路。对于经过网关的数据库请求，产品提供数据库行为审计能力，可对相关访问行为进行采集和记录。

这种部署位置使网关能够围绕经过自身的访问请求，采集 SQL 及相应访问信息，为后续审计和运行分析提供数据基础。DBPrisma 的价值不只是保存 SQL 文本，还包括将数据库访问过程纳入统一的代理入口和行为记录路径。

在实际项目中，应根据目标数据库、连接方式、产品版本和审计输出方式，核实可获得的字段及其语义。例如，客户端身份、数据库账号、来源地址、目标后端和执行结果等信息，应分别明确采集来源，不能将不同层次的身份混为一谈，也不能在未经验证时承诺所有接口都输出完全相同的字段集合。

DBPrisma 的审计数据可以作为企业现有审计和安全运营工作的输入。至于如何进行集中检索、跨系统关联、告警判断和事件处置，还需要结合客户现有平台、数据接口和运营流程设计，不能仅凭具备审计记录能力就推导为自动完成安全事件分析。

## 五、建立可追溯审计，需要把边界说清楚

企业评估数据库审计能力时，可以重点检查：是否记录 SQL 请求，是否能够区分请求与执行结果？是否能识别连接使用的客户端或应用身份？身份代表的是应用账号还是最终用户？是否记录访问来源及其采集口径？是否能够识别请求对应的目标数据库或后端？时间字段的含义、精度和时区是否明确？不同记录之间是否存在可用于关联的标识？审计数据如何输出、保存、检索和保护？

这些问题有助于把“有审计日志”进一步转化为可检查、可解释的审计能力。

**数据库审计的价值，不在于日志条目有多少，而在于能否为一次访问行为提供足够准确的上下文和可核验的线索。** DBPrisma 通过数据库访问链路上的行为采集与审计，为企业建立这类数据基础提供一种实现方式。最终能够回答哪些问题，仍应以具体版本、接入环境和实际输出记录为准。
