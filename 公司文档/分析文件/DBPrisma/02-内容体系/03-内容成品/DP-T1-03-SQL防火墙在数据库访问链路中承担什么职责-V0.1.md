# SQL 防火墙在数据库访问链路中承担什么职责

> 文章定位：技术解释型 + 观点/认知型  
> 选题编号：DP-T1-03  
> 版本：V0.1 初稿  
> 状态：内部审阅稿，未经发布审批

数据库安全体系中，防火墙、访问控制、数据库账号权限和审计等机制各有职责。当讨论数据库访问安全时，SQL 防火墙常常被赋予很高期待：有人希望它能够识别并阻断所有危险 SQL，也有人把它简单理解为一组 SQL 黑名单。

这两种理解都不够准确。

SQL 防火墙的核心职责，是在数据库访问链路上对 SQL 请求实施规则检查，并根据策略决定如何处理请求。它是一层针对数据库请求的安全控制，不是数据库安全的全部，也不能替代数据库自身的权限体系和其他安全机制。

## 一、为什么需要在 SQL 请求进入数据库前增加检查

数据库权限控制通常以账号、角色、对象和操作权限为基础。它回答的是：某个数据库身份在数据库内部被允许执行哪些操作。

但企业在实际运行中，还可能需要对进入数据库的 SQL 请求实施更细致的检查。例如，某类应用是否允许执行特定类型的语句，某些请求是否应当被记录或拦截，访问行为是否符合企业制定的规则。

这时，仅仅确认连接账号具有数据库权限，并不足以说明每一条请求都符合企业的访问策略。数据库访问链路上的 SQL 检查，可以为权限体系补充一层请求级控制。

需要强调的是，SQL 防火墙不能凭空判断业务意图。规则必须由企业结合应用用途、数据库对象、业务操作和风险要求进行设计、验证和维护。

## 二、SQL 防火墙的工作重点是规则检查，而不是简单匹配关键词

一条 SQL 语句包含语法结构、操作类型、对象引用和表达式等信息。若仅依靠简单字符串匹配，可能难以准确理解语句结构，也容易受到空白、注释、大小写或语法形式变化的影响。

因此，数据库访问控制需要结合 SQL 解析等基础能力理解请求结构，再根据具体规则进行判断。解析的作用是识别 SQL 结构，为后续规则检查提供基础；解析本身并不等于安全判断，更不意味着可以自动理解所有业务语义。

从职责上看，可以区分三个环节：

1. **请求识别：** 接收并识别进入网关的 SQL 请求；
2. **结构解析与规则检查：** 依据 SQL 结构和已配置规则进行判断；
3. **策略处理：** 根据规则配置对请求进行放行、记录或拦截等处理。

实际产品对不同语句类型、数据库协议和规则条件的支持范围，需要以具体版本和验证结果为准。不能把“具备 SQL Parser”直接表述为“能够识别所有风险 SQL”，也不能把规则检查等同于完整的 SQL 注入防护。

## 三、SQL 防火墙不能替代数据库原生安全机制

SQL 防火墙作用于经过其访问入口的 SQL 请求。它无法天然覆盖绕过网关直连数据库的访问，也不能替代数据库自身的账号权限、对象授权、审计配置和安全加固。

一个完整的数据库安全体系，通常需要不同层次的控制共同发挥作用：

- 网络和边界控制负责限制不应存在的网络访问路径；
- 身份和账号管理负责确认访问主体及凭据使用边界；
- 数据库原生权限负责数据库内部对象和操作授权；
- SQL 防火墙在访问链路上依据规则检查 SQL 请求；
- 审计机制记录访问行为，为调查和复核提供线索。

这些机制之间不是简单替代关系。SQL 防火墙的价值在于增加一层请求级策略控制，并使相应的策略处理发生在数据库访问链路上。

## 四、DBPrisma 如何提供 SQL 防火墙能力

DBPrisma 部署在现有数据库前，通过代理入口承接客户端数据库访问请求。产品提供 SQL 防火墙能力，可对经过网关的 SQL 请求实施规则检查，并按策略进行处理。

DBPrisma 同时具备 SQL Parser 能力。SQL 解析为理解请求结构提供基础，SQL 防火墙则承担依据规则进行检查和策略处理的职责。二者相关，但不能混为同一个概念：Parser 不是防火墙规则本身，具备 Parser 也不意味着自动具备全部安全规则。

在实际部署中，企业需要明确哪些应用流量经过 DBPrisma、哪些 SQL 规则适用于相应应用和数据库、策略命中后采取何种处理方式，以及如何验证规则不会对正常业务造成非预期影响。

规则上线前应当在授权测试环境中使用代表性 SQL 样本进行验证，并保留规则版本、测试结果和变更记录。对于业务影响较大的策略，应制定观察、启用和回退流程。

## 五、如何评估 SQL 防火墙是否适合当前治理需求

企业评估 SQL 防火墙时，可以重点确认：

- 哪些数据库和应用访问路径经过防火墙？
- 当前规则针对哪些 SQL 类型、对象或条件？
- 规则检查依据是字符串、解析结构还是其他上下文？
- 命中规则后是记录、放行还是拦截？是否可按策略配置？
- 正常业务 SQL 是否经过充分回归验证？
- 规则变更是否有审批、测试和回退机制？
- 是否保留策略处理结果及相关审计线索？
- 数据库是否仍存在绕过网关的直连路径？

这些问题能够帮助企业把“部署了 SQL 防火墙”转化为可验证的治理措施。

**SQL 防火墙不是替代数据库权限的万能防护，而是数据库访问链路上的一层请求级策略控制。** DBPrisma 通过代理接入、SQL Parser 和 SQL 防火墙能力，为企业在数据库前建立 SQL 请求检查与策略处理位置提供技术支撑。具体覆盖范围和规则效果，应以产品版本、配置和实际测试为准。
