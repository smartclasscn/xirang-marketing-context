## 二、微信公众号版本

### 标题
数据库安全治理，为什么需要关注访问路径？

### 导语
数据库安全建设常常从账号权限、网络边界、加密传输和审计日志入手。这些都重要，但还有一个容易被忽略的问题：业务应用究竟通过什么路径访问数据库？

当应用、数据库实例和安全控制点逐渐增多，连接入口、访问身份、来源地址、SQL 请求和审计记录可能分散在不同系统中。企业需要的不只是保护数据库本身，也需要看清并治理通往数据库的访问路径。

### 正文结构
1. 数据库安全治理为什么不能只看数据库内部
2. 一次数据库访问路径包含哪些环节
3. 分散控制点为什么增加统一治理和追溯难度
4. 统一代理访问入口能够承担什么职责
5. DBPrisma 如何参与身份校验、来源控制、SQL 防火墙、链路保护和行为审计
6. 企业自查清单与产品说明

微信公众号正文以官网母稿为准，可适当缩短第二、三节的解释段落；不得删除“应用层账号不等于自然人身份”“SQL 防火墙采用正则表达式匹配”“代理接入需要验证驱动、连接池、事务与会话行为”等关键边界。

### 结尾引导
如果正在梳理数据库访问入口、账号隔离、SQL 请求控制或审计追溯问题，可以结合现有数据库类型、应用连接方式和部署环境，评估是否需要在数据库前增加统一代理访问与治理层。具体适配范围应通过项目验证确认。

## 三、知乎 / CSDN 问答版

### 建议问题
数据库安全审计为什么不能只看数据库日志？应用到数据库之间的访问链路需要管控吗？

### 回答正文
数据库日志是数据库安全审计的重要信息来源，但只看数据库内部日志，未必能够完整回答一次访问从哪里发起、使用什么应用身份、经过哪些访问控制，以及最终如何进入后端数据库。

企业数据库访问通常涉及多个环节：应用连接配置、客户端身份、网络来源、代理或访问入口、SQL 请求、后端数据库和行为记录。如果这些信息分别由不同系统管理，安全团队在策略调整、异常调查和审计追溯时，就可能需要跨系统拼接上下文。

因此，数据库安全治理可以把应用到数据库之间的访问路径作为独立对象。一个常见做法是在应用与现有数据库之间部署数据库代理访问入口，在适用范围内集中实施连接管理、身份校验、来源控制、SQL 请求规则检查和行为采集。

DBPrisma 是息壤科技的数据库串行审计安全网关，部署在现有数据库前，提供代理接入、客户端身份校验、应用层账号与数据库底层账号物理隔离、访问控制、SQL 防火墙、数据路由、行为审计及数据库链路国密加密等能力。当前 SQL 防火墙采用正则表达式匹配规则；访问来源黑白名单针对 IP 地址。应用层账号不等于最终自然人身份，审计采集也不等于自动威胁检测。

引入代理入口并非所有环境都零改造。项目仍需验证数据库类型与连接协议、驱动、连接池、事务、会话状态和故障处理方式。数据库原生权限、网络安全体系和企业安全运营平台仍然承担各自职责。

所以，数据库审计不只是“有没有日志”，数据库安全也不只是“数据库内部有没有设置权限”。更重要的是，企业是否能够理解并治理从应用到数据库的完整访问过程。
